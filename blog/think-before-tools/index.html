02 / 一个意外的分岔

示范中调用得更多，后来却更少用了

我们的训练分成两步。先做监督微调（SFT）：让模型学习完整的解题示范，包括推理、调用工具、读取返回结果和回答。再做强化学习（RL）：让模型自己解题，根据最终答案是否正确来更新。这里，调用几次工具、调用前写多少推理，都没有额外奖励。

从同一个 Qwen2.5-VL-7B-Instruct 模型出发，我们准备了三组 SFT 数据。Low 的工具轨迹只调用一次，Medium 调用两到三次，High 至少调用四次。每组都有 2,000 条轨迹，其中 500 条不用工具的示范完全相同，总 token 预算也尽量匹配。模型可以使用 Zoom 放大图像，用 Code 运行 Python。之后，三组模型接受相同的 RL 训练。

一个自然的预期是：看过更多步工具交互的模型，之后也会更常使用工具。实际训练中，三组模型的答题正确率逐渐接近，工具使用却分开了。Low 越来越常调用工具；Medium 的调用比例整体下降；High 在早期就快速减少调用。

把训练完成后的模型放到评测集上，三组模型至少调用一次工具的题目比例，差距同样明显。

这里数的是一整次解题有没有启动工具。High 剩下的工具轨迹仍然包含较多次调用，所以不能仅凭启动率下降，就说它忘记了多步调用。它主要是更少选择进入这条解题路径了。

示范中的调用次数，显然还不足以解释这些行为。我们于是回头检查示范本身。

03 / 回到调用之前

那段推理，是一条值得追下去的线索

把工具轨迹拆开，会看到一个反复出现的过程：先推理，发出调用，读到结果，再继续推理或调用。我们把每次调用紧邻之前的推理文字称为 pre-call reasoning，也就是调用前推理。

三组数据在这里差别很大。Low 每次调用前平均有 623 个推理 token，Medium 是 302 个，High 只有 161 个。token 可以粗略理解成文本长度的计量单位。在 Code 工具上，这个差距更大：分别是 991、423 和 134 个。

也就是说，在近似的总 token 预算下，High 示范了更多次交互，却给每次调用之前的推理留下了更少文字。再看开头的例子，模型能写对工具调用格式，却没有先弄清楚“总收入”该包括哪些数。

我们还检查了 RL 前后的轨迹。在 Medium 和 High 留下来的工具轨迹中，前三次调用前的平均推理长度都增加了。以第一次调用为例，Medium 从 306 增到 391 个 token，High 从 266 增到 385 个。

这些观察指向一个假设：调用前的推理，可能影响工具决策是否有助于答对，也影响这类行为能否在 RL 中保留下来。但长度不等于质量。我们需要继续检验：展示了更多调用前推理的示范，能否给后续训练一个更好的起点？

只奖励最终答对的 RL，
会怎样对待一条容易出错的工具路径？

先想一想 RL 在奖励什么。对同一道题，模型可以用工具作答，也可以直接作答。如果使用工具的路径反而更容易失败，那么只奖励最终正确答案的训练，就可能降低这类路径出现的概率。训练目标里没有一项要求“保住 SFT 学过的调用次数”。

我们用一个简化的概率模型分析了这个过程。在这个理想化模型里，工具启动概率上升还是下降，取决于工具路径的成功率是否高于直接作答的路径。因此，两件事完全可能同时发生：模型更少选择工具，留下来的工具轨迹却更容易答对。

展开看：工具路径如何被选择性保留？

固定一道题，将完整解题轨迹分成使用工具和直接作答两类。记 I 为工具启动概率，C 为工具路径的成功率，D 为同一策略中不调用工具路径的成功率。论文的理想化动态满足：

dI/dt = I(1 − I)(C − D)

当 C > D 时，工具启动概率增加；当 C < D 时，它减少。模型之间在整体正确率和工具路径成功率上的初始优势，也能在这一理想化优化过程中保持。

这不是实际 GRPO 训练的精确方程，也不能直接证明推理长度带来了因果效果。这里的 D 指同一策略内部、不调用工具的轨迹分支，与后文关闭工具接口后的独立评测不同。

04 / 重新分配监督机会

选哪些示范，会改变接下来的训练

我们回到原始 High 数据，给每条工具轨迹算一个分数：每次调用前，平均有多少推理 token。按这个分数排序后，保留排在前面的完整轨迹，内容不作改写。

选择整条轨迹，内容不作改写。

03匹配累计监督量

在较小子集上训练更多轮，再做相同的 RL。

两个筛选子集叫 LF50 和 LF25，LF 是 Length-Filtered 的缩写。它们每轮包含的监督 token，约为原始 High 的 50% 和 25%。注意，这个比例说的是 token 量，不是样本条数。

为了近似匹配累计监督 token 量，原始 High 训练一轮，LF50 训练两轮，LF25 训练四轮，优化更新次数也保持一致。之后的 RL 和评测设置不变。我们比较的是同样多的监督机会怎样分配，而不是把训练预算缩减到原来的四分之一。

我们还加入了随机筛选的对照：保留与 LF25 近似相同的监督 token 量，采用相同的重复轮数、批大小、更新次数和后续 RL 设置。两者的区别只在于选了哪些示范。

05 / 把工具关掉，再比较一次

工具这次帮上忙了吗？

总体正确率提高以后，还需要再问一步：这个改进和工具使用有什么关系？一个直接的检查，是让同一个训练好的模型做两次评测，一次开放工具，一次关闭工具。

来源：论文表 3：开放工具 − 关闭工具 ↗

原始 High 开放工具时，反而比关闭工具少答对了一些题。换成 LF25，这个差值变成了正数，而且五个评测集上的差值全部为正。两者关闭工具后的总体正确率仍然接近。

工具是否更常被调用，则因任务而异。ChartQA 上，从 High 到 LF25，使用工具的题目比例从 2.2% 降到了 0.6%，开放工具时的正确率却从 85.48% 提高到 87.72%；MathVista 和 WeMath 上，工具启动比例有所增加。

所以，只数工具被叫了多少次，会漏掉这里最关键的变化。更值得一起检查的是：模型何时选择工具、这些解题轨迹有多容易成功，以及开放工具后最终能多答对多少题。

06 / 回到那道图表题

把调用之前的判断教清楚

两条轨迹都能调用 Python，也都能让代码运行起来。结果出现差别，是因为其中一条先确定了正确的分母。

这项研究让我们更重视 SFT 示范中这一段容易被忽略的内容：为什么需要这次调用，准备交给工具什么问题，又如何利用已经得到的信息继续往下走。在我们的实验里，按调用前推理长度筛选已有示范，就能改善后续 RL 的结果，让工具开放的整体收益由负转正。

长度只是一个容易计算的代理指标。筛选同时改变了模型看到哪些完整示范，因此不能把这些结果归结为“只要把推理写长就有效”。实验也集中在一个基础模型、Zoom 和 Code 两种工具，以及只奖励最终答案正确的 RL 设置。下一步更值得探索的，是如何直接识别那些把调用依据和计算目标讲清楚的示范。

“这里为什么要除以 815？”
是在工具开始工作之前，就需要回答的问题。

准备工具使用数据时，除了检查调用能不能执行，也读一读它前面的那段推理。模型为什么需要这次调用、准备交给工具什么问题，都值得在示范里讲清楚。
